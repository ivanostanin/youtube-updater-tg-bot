# Story 1.15: Telegram Channel Broadcast via DM Configuration

## Status

Done
---

## Story

**As a** Telegram channel owner who relies on private chats for configuration,  
**I want** to link my broadcast channel to the bot from a DM and manage its YouTube subscriptions without posting setup messages publicly,  
**so that** my audience receives automated video notifications while administrative controls stay private and secure.

---

## Acceptance Criteria

1. **AC1 (Channel linking over DM):** Provide a `/channel_link` DM command that prompts for a channel username/ID, verifies the requester is an administrator of that channel via `getChatMember`, fetches channel metadata (`chat_id`, title, username, invite link), and persists/updates it in the `chats` table with `chat_type='channel'`. Successful links reply with the resolved channel title and a reminder that all future configuration happens privately. *(Sources: docs/architecture/6-api-design-and-integration.md §6.2 Bot Commands; docs/architecture/5-component-architecture.md §5.1 Notification Pipeline; docs/prd/2-requirements.md §FR5 Group & Channel Support)*
2. **AC2 (Per-channel configuration context):** Add a `/channel_select` DM command (or inline keyboard) that lets an admin choose one of their linked channels as the active context. When a channel is selected, `/subscribe`, `/unsubscribe`, `/list`, and `/options` executed inside the DM apply to that channel instead of the admin’s personal chat, and responses clearly state the target channel name. *(Sources: docs/architecture/5-component-architecture.md §5.3 BotHandlers; docs/architecture/8-source-tree.md §8.2 Bot Layer; docs/prd/2-requirements.md §FR3 Bot Commands)*
3. **AC3 (Channel-bound notification dispatch):** Update the notification pipeline so that subscriptions created through DM channel context deliver messages to the linked channel chat_id with channel-appropriate formatting (no @user callouts, respect Markdown limitations, include source attribution). Ensure PubSub/webhook handlers resolve the correct chat context when enqueuing notifications. *(Sources: docs/architecture/5-component-architecture.md §5.4 NotificationService; docs/architecture/6-api-design-and-integration.md §6.4 Webhook Processing; docs/prd/2-requirements.md §FR6 Notifications)*
4. **AC4 (Access control & auditing):** Store the mapping between Telegram users and the channels they can administer (`channel_admin_links` table or equivalent) including role (`creator`, `administrator`) and timestamps. Enforce that only linked admins may run `/channel_select` or manage subscriptions for that channel, revoke access automatically if Telegram reports they are no longer admins, and log these events with structured context (`chat_id`, `user_id`, `operation`). *(Sources: docs/architecture/12-security-integration.md §12.2 Enhancement Security Requirements; docs/architecture/4-data-models-and-schema-changes.md §4.3 Database Changes; docs/prd/3-non-functional-requirements.md §NFR2 Security)*
5. **AC5 (Operator UX & documentation):** Update `.env.example`, `README.md`, and `CLAUDE.md` to document the DM-only channel onboarding flow, required permissions (admin rights + ability to post), and troubleshooting steps (e.g., bot must be added as channel admin). Provide inline DM guidance (help text, retry instructions) with localization hooks so AC1/AC2 flows remain translatable. *(Sources: docs/architecture/10-coding-standards.md §10.3 Documentation Expectations; docs/prd/5-ux.md §5.2 Admin Experience; README.md)*
6. **AC6 (Test coverage & monitoring):** Add unit/integration tests covering channel linking, selection, ACL enforcement, and notification dispatch (mocking Telegram API + webhook flow). Extend logging/metrics (e.g., `LinkChannelSuccess`, `ChannelSelectionDenied`) so dashboards can report how many channels are linked via DM. Tests must run in CI via `uv run pytest`. *(Sources: docs/architecture/11-testing-strategy.md §11.2 Integration Tests; docs/architecture/7-observability.md §7.1 Logging & Metrics; tests/unit/test_handlers.py)*
7. **AC7 (Bot permission verification):** During `/channel_link`, validate that the bot itself is already added to the target channel with the required admin permissions (`can_post_messages`, `can_edit_messages` if used, `can_delete_messages` for cleanup). If the bot lacks permissions, present localized remediation steps and block the link until permissions are granted. *(Sources: docs/prd/5-ux.md §5.2 Admin Experience; docs/architecture/12-security-integration.md §12.2 Enhancement Security Requirements; docs/architecture/6-api-design-and-integration.md §6.2 Bot Commands)*
8. **AC8 (Private channel compatibility):** Support linking and managing private Telegram channels (no public `@username`) by accepting invite links or numeric channel IDs, ensuring the bot can resolve and post to those chats, and masking invite tokens in logs. DM guidance must explain the extra steps admins need to take when onboarding private channels. *(Sources: docs/prd/2-requirements.md §FR5 Group & Channel Support; docs/architecture/6-api-design-and-integration.md §6.2 Bot Commands; docs/architecture/5-component-architecture.md §5.4 NotificationService)*
9. **AC9 (Channel unlink & cleanup):** Provide a `/channel_unlink` DM command that removes the association between an admin and the selected channel, soft-deletes or archives the channel entry, and purges all subscriptions/notification hooks tied to that channel (after confirmation). Responses must summarize the impact (“X subscriptions removed”) and log the action for auditing. *(Sources: docs/prd/3-non-functional-requirements.md §NFR2 Security; docs/architecture/6-api-design-and-integration.md §6.2 Bot Commands; docs/architecture/5-component-architecture.md §5.4 NotificationService)*

## Dev Notes

### Channel & Admin Data Model
- `chats` already store `chat_type`, so channel metadata should reuse this table while `channel_admin_links` keeps who may manage each channel.  
- When fetching admin status, cache Telegram responses briefly to avoid rate limits (per docs/architecture/12-security-integration.md §12.4 Rate Limits).  
- Revocation logic should run opportunistically (e.g., during failed command or scheduled job) to keep ACLs current.

### DM Command UX
- AC1/AC2 flows must keep all prompts inside DMs to avoid leaking channel configuration; use inline keyboards to select from multiple linked channels.  
- Provide contextual help text (localized) describing prerequisites: bot must already be added as channel admin with “can post” permission.
- Forwarded messages from private channels should switch the DM context automatically (after `/channel_link`), so admins can re-target channels without exposing invite links.

### Integration Verification Requirements
1. **IV1:** Admin can successfully link a channel via DM and receive confirmation including channel title/username.  
2. **IV2:** Selected channel context causes `/subscribe` and `/list` to operate on the channel, not the admin’s private chat.  
3. **IV3:** Attempting to manage an unlinked channel (or after admin rights are revoked) fails with clear error and log entry.  
4. **IV4:** PubSub/webhook notification for a linked subscription posts to the channel with expected formatting.  
5. **IV5:** Metrics/logs emit `LinkChannelSuccess` and `ChannelDelivery` entries for observability dashboards.  
6. **IV6:** `uv run pytest` (unit + integration suites) passes.

### Risks & Mitigations
- **Telegram permission drift:** Periodically re-verify admin rights and surface warnings in DM if the bot loses posting permission.  
- **Context confusion:** Provide `/channel_status` helper and proactive warnings when no channel is selected to avoid misrouted subscriptions.  
- **Security exposure:** Store minimal personally identifiable information and redact channel invite links from logs per security guidance.

### QA Review – 2025-11-17

- **Owner:** Quinn (Test Architect)
- **Scope:** Re-test Story 1.15 implementation against AC2/AC6/AC8 after the latest handler and docs updates. Verified targeted channel handler unit tests with `uv run pytest tests/unit/test_handlers.py -k channel`.

**Issues Identified**
1. **/unsubscribe keeps running after channel context expires (AC2):** When `_build_command_context` clears a stale or revoked channel selection, `/unsubscribe` notifies the user but never returns (`src/bot/handlers.py:2377-2388`). The handler immediately falls back to the admin’s DM `chat_id`, so the user can unknowingly unsubscribe their personal chat even though they just saw “channel context expired”. Every other DM command (`/subscribe`, `/list`, `/channel_unlink`, and the unsubscribe callback) stops execution once the context is cleared, so this asymmetry is a real functional regression against AC2’s requirement that DM commands explicitly target the selected channel.
2. **No integration coverage for the DM channel workflow (AC6):** The integration suite still only exercises legacy personal-chat flows (`tests/integration/test_bot_flow.py:1-220`) and repository helpers. There are zero end-to-end tests that drive `/channel_link`, `/channel_select`, ACL revocation, or DM-to-channel notification dispatch, despite the test plan calling for scenarios 1.15-INT-003‒008. This leaves the riskiest parts of Story 1.15 untested in CI.

**Gate Status:** **FAIL** – Story 1.15 cannot ship until `/unsubscribe` stops operating on stale contexts, and the promised integration tests exist to guard the DM channel workflow.

### QA Review – 2025-11-27

- **Owner:** Quinn (Test Architect)
- **Scope:** Runtime ACL enforcement plus the Story 1.15 code/test deliverables (handlers, repositories, CI suites).

**Issues Identified**
1. **Channel commands keep working after admins are revoked (AC4):** `_build_command_context` only ensures a cached `channel_admin_links` row exists (`src/bot/handlers.py:285-317`) and every DM command simply trusts that context when mutating subscriptions (`src/bot/handlers.py:2300-2379`). The only place `ACLService.verify_admin` runs for channels is inside the `/channel_select` callback (`src/bot/handlers.py:1174-1195`), so once a channel is linked or selected the user can continue driving `/subscribe`/`/unsubscribe`/`/list` even if Telegram has already removed their admin role. AC4 explicitly calls for revoking access as soon as Telegram reports the loss of admin rights, so this is a security gap.
2. **Planned channel-selection/ACL/notification tests never landed (AC6):** The approved test matrix lists scenarios `1.15-INT-003/004/005/006/007` and `1.15-UNIT-003` (`docs/qa/assessments/1.15-test-design-20251116.md:30-66`), yet the codebase still only contains the legacy `/channel_link` unit tests (`tests/unit/test_handlers.py:815-969`), no repository coverage for `ChannelAdminLinkRepository` (`tests/unit/test_repository.py:13-21`), and integration tests that never invoke `/channel_link` or `/channel_select` (`tests/integration/test_bot_flow.py:29-190`). Without those tests, CI cannot verify the DM-channel workflow, ACL revocation, or notification routing that AC6 demands.
3. **Private-channel invite links don’t update context (AC2/AC8):** `/channel_link` happily parses invite URLs and upserts channel metadata, but it only sets the DM’s active context if the admin runs `/channel_select` afterwards. Sending only the invite link leaves `target_chat` pointing to the DM, so `/subscribe` continues to manage the user’s private chat even though the channel was linked, contradicting the documented private-channel onboarding flow.

**Gate Status:** **FAIL** – see `docs/qa/gates/1.15-telegram-channel-dm-config.yml` for the formal decision and remediation checklist.

### QA Review – 2025-03-18

- **Owner:** Quinn (Test Architect)
- **Scope:** AC5/AC8 deliverables plus observability for the DM-channel workflows.

**Issues Identified**
1. **Invite-link onboarding still breaks for private channels (AC8):** `_normalize_channel_identifier` strips everything before the last `/` and forcibly prefixes `@` for any non-numeric token (`src/bot/handlers.py:215-245`), so an invite such as `https://t.me/+SecretToken` becomes `@+SecretToken`. Telegram rejects that username, causing `/channel_link` to error before it can resolve or persist the private channel even though AC8 requires invite-link compatibility.
2. **Operator documentation never mentions permissions or remediation (AC5):** The files explicitly called out in AC5 still lack the required instructions: `README.md` documents `/channel_link` but omits the admin-permission prerequisites or troubleshooting guidance (`README.md:45-55`), `.env.example` only adds a TTL knob with zero context about DM onboarding or bot permissions (`.env.example:1-40`), and `CLAUDE.md` repeats the old command list without noting that the bot must already be an admin with post/delete rights (`CLAUDE.md:40-105`). This leaves operators without the mandated guidance on DM-only setup and recovery steps.
3. **No debug trace for forwarded-channel extraction (AC6 / observability):** `_extract_forwarded_channel` silently returns `None` when it cannot parse the forwarded metadata (`src/bot/handlers.py:423-434`). Because `/channel_link` relies on forwards for invite-only channels, the absence of `self._debug` statements makes it impossible to diagnose why a DM attempt failed, violating the logging expectations in AC6’s observability clause.

**Gate Status:** **FAIL** – see `docs/qa/gates/1.15-telegram-channel-dm-config.yml` for the updated decision and remediation checklist.
