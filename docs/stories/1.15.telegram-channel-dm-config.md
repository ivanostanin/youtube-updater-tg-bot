# Story 1.15: Telegram Channel Broadcast via DM Configuration

## Status

Ready for Review

---

## Story

**As a** Telegram channel owner who relies on private chats for configuration,  
**I want** to link my broadcast channel to the bot from a DM and manage its YouTube subscriptions without posting setup messages publicly,  
**so that** my audience receives automated video notifications while administrative controls stay private and secure.

---

## Acceptance Criteria

1. **AC1 (Channel linking over DM):** Provide a `/channel_link` DM command that prompts for a channel username/ID, verifies the requester is an administrator of that channel via `getChatMember`, fetches channel metadata (`chat_id`, title, username, invite link), and persists/updates it in the `chats` table with `chat_type='channel'`. Successful links reply with the resolved channel title and a reminder that all future configuration happens privately. *(Sources: docs/architecture/6-api-design-and-integration.md §6.2 Bot Commands; docs/architecture/5-component-architecture.md §5.1 Notification Pipeline; docs/prd/2-requirements.md §FR5 Group & Channel Support)*
2. **AC2 (Per-channel configuration context):** Add a `/channel_select` DM command (or inline keyboard) that lets an admin choose one of their linked channels as the active context. When a channel is selected, `/subscribe`, `/unsubscribe`, `/list`, and `/options` executed inside the DM apply to that channel instead of the admin’s personal chat, and responses clearly state the target channel name. *(Sources: docs/architecture/5-component-architecture.md §5.3 BotHandlers; docs/architecture/8-source-tree.md §8.2 Bot Layer; docs/prd/2-requirements.md §FR3 Bot Commands)*
3. **AC3 (Channel-bound notification dispatch):** Update the notification pipeline so that subscriptions created through DM channel context deliver messages to the linked channel chat_id with channel-appropriate formatting (no @user callouts, respect Markdown limitations, include source attribution). Ensure PubSub/webhook handlers resolve the correct chat context when enqueuing notifications. *(Sources: docs/architecture/5-component-architecture.md §5.4 NotificationService; docs/architecture/6-api-design-and-integration.md §6.4 Webhook Processing; docs/prd/2-requirements.md §FR6 Notifications)*
4. **AC4 (Access control & auditing):** Store the mapping between Telegram users and the channels they can administer (`channel_admin_links` table or equivalent) including role (`creator`, `administrator`) and timestamps. Enforce that only linked admins may run `/channel_select` or manage subscriptions for that channel, revoke access automatically if Telegram reports they are no longer admins, and log these events with structured context (`chat_id`, `user_id`, `operation`). *(Sources: docs/architecture/12-security-integration.md §12.2 Enhancement Security Requirements; docs/architecture/4-data-models-and-schema-changes.md §4.3 Database Changes; docs/prd/3-non-functional-requirements.md §NFR2 Security)*
5. **AC5 (Operator UX & documentation):** Update `.env.example`, `README.md`, and `CLAUDE.md` to document the DM-only channel onboarding flow, required permissions (admin rights + ability to post), and troubleshooting steps (e.g., bot must be added as channel admin). Provide inline DM guidance (help text, retry instructions) with localization hooks so AC1/AC2 flows remain translatable. *(Sources: docs/architecture/10-coding-standards.md §10.3 Documentation Expectations; docs/prd/5-ux.md §5.2 Admin Experience; README.md)*
6. **AC6 (Test coverage & monitoring):** Add unit/integration tests covering channel linking, selection, ACL enforcement, and notification dispatch (mocking Telegram API + webhook flow). Extend logging/metrics (e.g., `LinkChannelSuccess`, `ChannelSelectionDenied`) so dashboards can report how many channels are linked via DM. Tests must run in CI via `uv run pytest`. *(Sources: docs/architecture/11-testing-strategy.md §11.2 Integration Tests; docs/architecture/7-observability.md §7.1 Logging & Metrics; tests/unit/test_handlers.py)*
7. **AC7 (Bot permission verification):** During `/channel_link`, validate that the bot itself is already added to the target channel with the required admin permissions (`can_post_messages`, `can_edit_messages` if used, `can_delete_messages` for cleanup). If the bot lacks permissions, present localized remediation steps and block the link until permissions are granted. *(Sources: docs/prd/5-ux.md §5.2 Admin Experience; docs/architecture/12-security-integration.md §12.2 Enhancement Security Requirements; docs/architecture/6-api-design-and-integration.md §6.2 Bot Commands)*

## Dev Notes

### Channel & Admin Data Model
- `chats` already store `chat_type`, so channel metadata should reuse this table while `channel_admin_links` keeps who may manage each channel.  
- When fetching admin status, cache Telegram responses briefly to avoid rate limits (per docs/architecture/12-security-integration.md §12.4 Rate Limits).  
- Revocation logic should run opportunistically (e.g., during failed command or scheduled job) to keep ACLs current.

### DM Command UX
- AC1/AC2 flows must keep all prompts inside DMs to avoid leaking channel configuration; use inline keyboards to select from multiple linked channels.  
- Provide contextual help text (localized) describing prerequisites: bot must already be added as channel admin with “can post” permission.

### Integration Verification Requirements
1. **IV1:** Admin can successfully link a channel via DM and receive confirmation including channel title/username.  
2. **IV2:** Selected channel context causes `/subscribe` and `/list` to operate on the channel, not the admin’s private chat.  
3. **IV3:** Attempting to manage an unlinked channel (or after admin rights are revoked) fails with clear error and log entry.  
4. **IV4:** PubSub/webhook notification for a linked subscription posts to the channel with expected formatting.  
5. **IV5:** Metrics/logs emit `LinkChannelSuccess` and `ChannelDelivery` entries for observability dashboards.  
6. **IV6:** `uv run pytest` (unit + integration suites) passes.

### Risks & Mitigations
- **Telegram permission drift:** Periodically re-verify admin rights and surface warnings in DM if the bot loses posting permission.  
- **Context confusion:** Provide `/channel_status` helper and proactive warnings when no channel is selected to avoid misrouted subscriptions.  
- **Security exposure:** Store minimal personally identifiable information and redact channel invite links from logs per security guidance.
