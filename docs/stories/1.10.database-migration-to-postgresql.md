# Story 1.10: Database Migration to PostgreSQL

## Status

Draft

---

## Story

**As a** system architect,  
**I want** to migrate the persistence layer from SQLite to PostgreSQL,  
**so that** the bot scales to thousands of concurrent subscriptions without lock contention or latency regressions.

> Trigger: Initiate once SQLite p95 latency exceeds 1 s, concurrent users >500, or lock errors >1% (docs/prd/4-epic-story-structure.md).

---

## Acceptance Criteria

1. **AC1 – Dependency Updates:** Add the asyncpg driver (and SQLAlchemy postgres extras) to `pyproject.toml` / lockfiles, ensuring local and CI environments install the PostgreSQL stack (docs/prd/4-epic-story-structure.md, docs/architecture/3-tech-stack.md#L13).
2. **AC2 – Managed Database Provisioning:** Stand up a managed PostgreSQL instance (OCI, RDS, or Cloud SQL) with HA, automated backups, and observability hooks documented in CLAUDE.md (docs/prd/4-epic-story-structure.md, docs/architecture/9-infrastructure-and-deployment.md).
3. **AC3 – Helm & Settings:** Extend the Helm chart and configuration templates (`values.yaml`, `.env.example`, `src/utils/config.py`) with PostgreSQL host, port, database, credentials, and connection pool sizing aligned with architecture guidance (docs/prd/4-epic-story-structure.md, docs/architecture/9-infrastructure-and-deployment.md#9.2).
4. **AC4 – Migration Script:** Author `scripts/migrate-sqlite-to-postgres.py` that exports SQLite data, recreates schema via Alembic on PostgreSQL, imports data with integrity checks, and logs a rollback plan (docs/prd/4-epic-story-structure.md, docs/architecture/4-data-models-and-schema-changes.md#4.3.3).
5. **AC5 – Runtime Switch:** Update the runtime `DATABASE_URL` resolution and SQLAlchemy engine creation so the bot prefers PostgreSQL when env vars are present, while retaining SQLite compatibility for dev (docs/prd/4-epic-story-structure.md, docs/architecture/2-enhancement-scope-and-integration-strategy.md).
6. **AC6 – Test Suite on PostgreSQL:** Ensure the full pytest suite (unit + integration) runs successfully against PostgreSQL in CI, capturing coverage + Allure artifacts with zero regressions (docs/prd/4-epic-story-structure.md AC6, docs/architecture/11-testing-strategy.md).
7. **AC7 – Staging Load Test:** Deploy to staging, execute load tests with ≥100 concurrent subscription operations, and document observed metrics (latency, lock errors) meeting targets (docs/prd/4-epic-story-structure.md AC7, IV4/IV5).
8. **AC8 – Documentation & Rollback:** Update CLAUDE.md with a detailed migration + rollback runbook, including cutover sequencing, verification steps, and how to revert to SQLite if needed (docs/prd/4-epic-story-structure.md AC8, docs/architecture/9.3).
9. **AC9 – Performance Evidence:** Provide a short report (CLAUDE.md or docs/architecture/appendix) proving p95 query latency <200 ms, throughput >100 req/s, and 0% lock errors post-migration (docs/prd/4-epic-story-structure.md AC9, Integration Verification IV4/IV5, NFR16 in docs/prd/2-requirements.md).

## Dev Notes

### Trigger Conditions & KPIs
- Migration is optional until scalability thresholds are breached; treat this story as blocking once the monitoring dashboard shows p95 latency >1 s, concurrent users >500, or SQLite lock errors >1% (docs/prd/4-epic-story-structure.md).  
- Performance targets post-cutover: p95 <200 ms, throughput >100 req/s, 0% lock errors under load (Integration Verification IV4–IV5).

### Schema & Driver Considerations
- SQLAlchemy remains the abstraction layer; only connection strings and drivers change (docs/prd/2-requirements.md NFR16).  
- Ensure Alembic migrations run against PostgreSQL before data import to guarantee schema parity (`alembic upgrade head`).  
- Connection pooling guidance: `pool_size=20`, `max_overflow=40` (docs/prd/4-epic-story-structure.md Technical Notes).  
- Keep SQLite compatibility for developers without PostgreSQL; gating via env vars ensures local DX continuity.

### Deployment & Ops
- Helm chart should support toggling between SQLite PVC and PostgreSQL DSN; document secrets + Kubernetes `Secret` templates (docs/architecture/9-infrastructure-and-deployment.md).  
- Backups: rely on managed PostgreSQL automated snapshots + pg_dump before cutover; update CLAUDE.md runbook accordingly.  
- Monitoring: add Grafana panels for PostgreSQL latency/locks; wire alerts when error rates exceed target.

### Testing & Tooling
- CI needs ephemeral PostgreSQL service for integration tests; reuse GitHub Actions services or docker-compose job (docs/architecture/11-testing-strategy.md).  
- Load testing can reuse existing scripts from deployment folder or new `scripts/load-test-postgres.py` (if needed) to exercise `/subscribe`, `/list`, `/unsubscribe`, and webhook flows end-to-end.  
- Ensure Allure tagging differentiates PostgreSQL regression suite (e.g., `@allure.story("PostgreSQL Migration")`).

### Risks & Mitigations
- **Data integrity risk:** Mitigate with checksum + row-count validation plus dry-run in staging.  
- **Downtime risk:** Plan blue/green cutover; keep SQLite in read-only mode until verification passes (docs/architecture/9.2).  
- **Cost/complexity:** Document infra cost impacts and ensure secrets rotation (managed service IAM) before production rollout.

### Integration Verification Requirements
- **IV1:** Row counts between SQLite and PostgreSQL match after migration (per-table checks).  
- **IV2:** Bot commands (`/subscribe`, `/list`, `/unsubscribe`) behave identically using PostgreSQL.  
- **IV3:** Webhook notifications continue to deliver updates without regressions.  
- **IV4:** Performance report proves latency/throughput improvements (targets above).  
- **IV5:** Load test shows zero PostgreSQL lock errors with ≥50 concurrent subscription mutations.

### Definition of Done
- All acceptance criteria validated locally and in CI/staging.  
- Documentation (CLAUDE.md, README.md, Helm values) updated and reviewed.  
- Metrics + load-test artifacts stored in repo/docs.  
- Story status updated to “Ready for Dev” once PO validation completes.
