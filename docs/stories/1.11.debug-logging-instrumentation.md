# Story 1.11: Add Debug Logging Coverage for Bot & Webhook Operations

## Status

Ready for Dev

---

## Story

**As a** support engineer who triages production incidents,  
**I want** consistent debug-level instrumentation across Telegram handlers, services, and webhook operations,  
**so that** I can trace subscriber issues end-to-end without reproducing them in production.

---

## Acceptance Criteria

1. **AC1 (Logging Blueprint & Config):** Document a logging blueprint in `CLAUDE.md` that lists required context keys (`chat_id`, `chat_type`, `user_id`, `channel_id`, `subscription_id`, `video_id`, `operation`, `request_id`) and redaction rules (no access tokens, API keys, or user messages). Update `src/utils/logging.py` (or a new helper) so handlers/services share a `LoggerAdapter` or helper that injects those keys, and clarify in `.env.example` that `LOG_LEVEL=DEBUG` enables the new traces.
2. **AC2 (Bot Handler Instrumentation):** Add debug logs before and after every handler in `src/bot/handlers.py` (`start`, `help`, `subscribe`, `list`, `unsubscribe`, message ingestion, callback flows, `_require_admin`, `manage_channel_webhook`, `handle_youtube_url`). Each log must include the standardized context keys, decision outcomes (e.g., channel_id resolved, webhook action taken), and sanitized user/channel names (truncate to 60 chars, no raw messages).
3. **AC3 (Subscription & ACL Operations):** Instrument repository-facing flows (`SubscriptionRepository` create/get/delete, `check_if_channel_has_other_subscribers`, ACL enforcement in `src/services/acl.py`) so we can trace whether a subscription already exists, why ACL checks failed, and how many active subscribers remain when deciding webhook actions.
4. **AC4 (PubSub & Webhook Pipelines):** Enhance `src/webhooks/handlers.py`, `src/webhooks/pubsub.py`, and `src/webhooks/synchronizer.py` with debug logs covering inbound webhook metadata, per-entry processing (video_id, channel_id, subscriber count, notification count), PubSub HTTP request/response codes, and synchronization decisions (legacy vs. current callback URLs).
5. **AC5 (Notification & External Clients):** Add debug logs in `src/bot/notifications.py`, `src/youtube/api.py`, and `src/services/acl.py` (Telegram send, YouTube API lookups, ACL verification) that surface request parameters, HTTP status codes, retries, and masked errors while keeping secrets redacted. Ensure notification attempts emit unique identifiers so they correlate with webhook events.
6. **AC6 (Validation & Docs):** Extend the pytest suite (e.g., `tests/unit/test_handlers.py`) with at least two tests that assert the new debug log entries via `caplog`, and update `README.md`/`CLAUDE.md` with a “Debugging Playbook” snippet showing how to enable DEBUG logs and interpret the context keys.

## Dev Notes

### Logging Baseline

- `src/utils/logging.py` already centralizes handler creation, honors `settings.log_level`, and routes logs to stdout + `logs/bot.log` *(Source: src/utils/logging.py)*.  
- Architecture standards require structured logging with contextual identifiers (`docs/architecture/10-coding-standards.md#10.3`). The new instrumentation must reuse those standards instead of ad-hoc strings.  
- Deployment guidance expects JSON-friendly logs shipped to Fluentd/Loki *(docs/architecture/9-infrastructure-and-deployment.md#9.2 Logging)*, so new entries should be key/value friendly (either JSON or `key=value` pairs).

### Bot & Service Touchpoints

- `src/bot/handlers.py` owns all Telegram command flows plus webhook management; it presently logs only warnings/errors for a few branches. Rich entry/exit tracing is needed for `/subscribe`, `/list`, `/unsubscribe`, inline callbacks, and ad-hoc URL ingestion *(docs/architecture/8-source-tree.md#8.1)*.  
- ACL enforcement lives in `src/services/acl.py` and currently logs only warnings; we need debug statements for every verification to explain denials.  
- Notification delivery (`src/bot/notifications.py`), PubSub orchestration (`src/webhooks/pubsub.py`, `src/webhooks/synchronizer.py`), and webhook ingestion (`src/webhooks/handlers.py`) must expose identifiers such as `channel_id`, `video_id`, and subscriber counts to close the loop from inbound webhook to outbound Telegram message.  
- External integrations (`src/youtube/api.py`, Telegram Bot API) should log status codes and request IDs without leaking tokens.

### Testing & Tooling References

- Follow the existing pytest guidance in `docs/architecture/11-testing-strategy.md#11.1` for unit vs. integration splits; `tests/unit/test_handlers.py` already exercises handler flows and is the right place for new `caplog` assertions.  
- Use ruff formatting rules (`docs/architecture/10-coding-standards.md#10.1`) when touching shared files.

### Risks & Constraints

- **PII exposure:** Logging must redact Telegram usernames or titles longer than 60 chars and never include message bodies.  
- **Noise explosion:** DEBUG logs should be silent when `LOG_LEVEL` is INFO to avoid overwhelming stdout in production.  
- **Performance:** Instrumentation must avoid expensive string formatting unless the log level is enabled (use `%s` formatting or lazy adapters).

### Integration Verification Requirements

- **IV1:** With `LOG_LEVEL=DEBUG`, running `/subscribe` in a dev chat logs a start/finish pair that includes `chat_id`, `user_id`, `channel_id`, webhook action, and subscription status.  
- **IV2:** Triggering a webhook notification logs the incoming feed metadata, the number of subscribers notified, and the notification IDs written to the database.  
- **IV3:** Executing `WebhookSubscriptionSynchronizer.run()` logs every channel evaluated, including decisions to skip or refresh and the HTTP results from the PubSub hub.  
- **IV4:** Unit tests using `caplog` in `tests/unit/test_handlers.py` pass and assert that debug entries contain the standardized context keys.

### Definition of Done

- All acceptance criteria satisfied and validated locally.  
- Tests (existing + new logging assertions) pass in CI.  
- Documentation updated (`CLAUDE.md`, `.env.example`, README snippet).  
- Story status moved to "Ready for Dev" with clear scope boundaries.
