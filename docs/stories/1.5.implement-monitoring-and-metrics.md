# Story 1.5: Implement Monitoring and Metrics

## Status

Draft
---

## Story

**As a** system operator,  
**I want** application metrics and structured logging,  
**so that** I can monitor bot health and troubleshoot production issues quickly.

---

## Acceptance Criteria

1. **AC1:** Add Prometheus metrics endpoint to the webhook server at `/metrics`.  
2. **AC2:** Implement counters: `telegram_commands_total` (labeled by command), `webhook_notifications_received_total`, `youtube_api_calls_total`.  
3. **AC3:** Implement gauges: `subscription_count`, `active_users_count`.  
4. **AC4:** Implement histogram: `notification_delivery_latency_seconds`.  
5. **AC5:** Configure JSON structured logging with context fields (`timestamp`, `level`, `message`, `user_id`, `chat_id`, `channel_id`).  
6. **AC6:** Add (or update) health check endpoint `/health` to return 200 OK with JSON payload and uptime.  
7. **AC7:** Update Helm chart to include liveness/readiness probes hitting `/health`.  
8. **AC8:** Provide an example Grafana dashboard JSON (stored under `docs/observability/`) covering key metrics.  
9. **AC9:** Document metrics, logging format, and dashboard usage in `CLAUDE.md`.

*(Source: docs/prd/4-epic-story-structure.md#story-15-implement-monitoring-and-metrics; docs/prd/3-technical-constraints-integration.md#deployment-risks)*

## Dev Notes

### Observability Baseline
- Infrastructure strategy already mandates Prometheus metrics and JSON logs shipped through Fluentd/Loki. The story must align with those expectations rather than inventing new tooling.  
  *[Source: docs/architecture/9-infrastructure-and-deployment.md#monitoring]*  
- Coding standards require contextual logging (user/chat/video identifiers). The JSON formatter should reuse these fields for consistency with existing handlers.  
  *[Source: docs/architecture/10-coding-standards.md#103-critical-integration-rules]*  

### Technical Constraints & Dependencies
- This story depends on prior stories delivering configuration hygiene (1.1), backups (1.2), and CI (1.4) so metrics deployment can piggyback on the stabilized pipeline. Group/chat schema (1.9) ensures gauges can rely on `Chat` model counts.  
  *[Source: docs/prd/4-epic-story-structure.md#story-15-implement-monitoring-and-metrics]*  
- Metrics collection must avoid blocking event loop code. Prefer non-blocking counters or background tasks to update expensive gauges.  
- Health endpoint must align with Kubernetes liveness/readiness probe requirements (rapid success/fail, small payload).  
  *[Source: docs/prd/3-technical-constraints-integration.md#health-checks]*  

### Testing Strategy
- Follow the existing pytest layout (unit vs. integration) and add caplog-based assertions to confirm JSON log payloads contain the mandated context fields.  
  *[Source: docs/architecture/11-testing-strategy.md#111-integration-with-existing-tests]*  
- Integration tests should exercise `/metrics` and `/health` routes via Starlette’s test client, verifying Prometheus exposition formatting and JSON payload schema.  
  *[Source: docs/architecture/11-testing-strategy.md#1122-integration-tests]*  
- Consider adding smoke tests that toggle gauges/counters to ensure they register once (idempotent import).  

### Integration Verification Requirements
- **IV1:** `curl /metrics` returns Prometheus text exposition with all collectors present.  
- **IV2:** Executing `/start`, `/subscribe`, `/list` increments the corresponding command counter labels (validated via automated test).  
- **IV3:** Publishing a webhook payload increments `webhook_notifications_received_total` and logs notification latency histogram observations.  
- **IV4:** Helm liveness/readiness probes succeed in dev cluster; Prometheus annotations allow scraping without manual serviceMonitor resources.  
- **IV5:** JSON logs captured from any handler include `user_id`/`chat_id` fields (null allowed) and redact sensitive tokens.  

### Risk Mitigation
- **Performance Noise:** Ensure histogram buckets are tailored (e.g., `0.1, 0.25, 0.5, 1, 2, 5 seconds`) to avoid high-cardinality metrics.  
- **Secrets Exposure:** Keep log context sanitized; never log entire Telegram messages or API keys.  
- **Collector Conflicts:** Guard against duplicate metric registration when running tests by clearing registry in fixtures.  

### Known Limitations
- Initial Grafana dashboard is sample-only; operators must import into their Grafana instance manually.  
- Cluster-level scraping configuration (Prometheus Operator, ServiceMonitor CRDs) is out of scope.  
- SQLite-based gauges may lag under heavy load because counts require DB scans; acceptable for MVP.  

### Future Enhancements (Out of Scope)
- Introduce alert rules (PagerDuty/Slack) once metrics stabilize.  
- Emit trace IDs (OpenTelemetry) for correlation with distributed traces.  
- Add per-channel subscription metrics to forecast growth trends.
