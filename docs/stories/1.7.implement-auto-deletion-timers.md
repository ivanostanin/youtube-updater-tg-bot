# Story 1.7: Implement Auto-Deletion Timers (Phase 2 Feature)

## Status

Draft
---

## Story

**As a** Telegram user,  
**I want** notifications automatically deleted after a configurable time period,  
**so that** my chat doesn't get cluttered with old video notifications.

---

## Acceptance Criteria

1. **AC1:** Add `auto_delete_after_days` column to `chats` table (nullable, default: null = disabled)  
2. **AC2:** Create Alembic migration for schema change  
3. **AC3:** Implement `/settings` command to configure auto-deletion (options: 1, 3, 7 days, or disable)  
4. **AC4:** Store `message_id` when sending notifications (already exists in `notifications` table)  
5. **AC5:** Create background task that runs hourly to find and delete old messages  
6. **AC6:** Delete messages using Telegram API `deleteMessage()` method  
7. **AC7:** Handle errors gracefully (message already deleted, bot removed from chat, insufficient permissions)  
8. **AC8:** Update CLAUDE.md and README.md with new feature documentation  
9. **AC9:** Add tests for auto-deletion logic (unit tests for selection, integration test for deletion)

## Dev Notes

### Auto-Deletion Preferences Surface
- Auto-delete must default to disabled so existing chats behave identically until they opt-in.  
  *[Source: docs/prd/4-epic-story-structure.md#story-17-implement-auto-deletion-timers-phase-2-feature]*  
- Although AC specifies a `chats.auto_delete_after_days` column, keep the implementation aligned with the PreferenceManager abstraction so future settings (quiet hours, templates) reuse the same `/settings` flow.  
  *[Source: docs/architecture/5-component-architecture.md#513-preferencemanager]*

### Background Scheduling & Rate Limiting
- Scheduler should run at most once per hour to balance prompt deletions and Telegram rate limits; leverage asyncio semaphores or APScheduler job queues for burst control.  
  *[Source: docs/prd/4-epic-story-structure.md#story-17-implement-auto-deletion-timers-phase-2-feature; docs/architecture/5-component-architecture.md#512-deletionscheduler]*  
- Maintain retry metadata (`attempts`, `status`) via `DeletionQueue` to provide observability and avoid repeated deletes for already-completed items.  
  *[Source: docs/architecture/4-data-models-and-schema-changes.md#413-deletionqueue]*

### Error Handling & Observability
- Recover gracefully when Telegram returns 400/403 errors by marking entries failed and surfacing actionable logs; avoid crashing the hourly loop.  
  *[Source: docs/prd/4-epic-story-structure.md#story-17-implement-auto-deletion-timers-phase-2-feature]*  
- Emit structured logs/metrics capturing counts of deleted messages, skipped entries, and rate-limit sleeps to support SLO tracking.  
  *[Source: docs/architecture/2-enhancement-scope-and-integration-strategy.md#221-code-integration-strategy]*

### Testing Strategy
- Unit tests should cover PreferenceManager helpers, scheduler selection logic, and Telegram deletion adapter stubs with retries/backoff paths.  
  *[Source: docs/architecture/11-testing-strategy.md#1121-unit-tests-for-new-components]*  
- Integration tests must simulate enabling auto-delete for a chat, sending notifications, and verifying the job deletes them without touching chats that left the default disabled state.  
  *[Source: docs/architecture/11-testing-strategy.md#1122-integration-tests]*  
- Continue running regression suite to ensure subscription creation and notification delivery remain unaffected when auto-delete is disabled.  
  *[Source: docs/architecture/11-testing-strategy.md#111-integration-with-existing-tests]*

### Integration Verification Requirements
- **IV1:** Existing notifications without auto-delete continue working normally.  
- **IV2:** Users/chats without auto-delete configured are unaffected.  
- **IV3:** Subscription/unsubscribe functionality continues working.  
- **IV4:** Database migration runs successfully (add column without data loss).  
- **IV5:** Background task runs without blocking bot operations.  
  *[Source: docs/prd/4-epic-story-structure.md#story-17-implement-auto-deletion-timers-phase-2-feature]*

### Risk Mitigation
- Ensure Alembic downgrade path and DB backups exist before deploying schema change.  
- Guard background job behind feature flag/env var so it can be paused if Telegram errors spike.  
- Rate-limit deletion batches to avoid hitting Telegram’s 30 req/sec ceiling; add jitter between batches if needed.

### Known Limitations
- Auto-deletion relies on bot remaining in the chat; if removed, queued deletions will fail and log warnings until entries expire manually.  
- Feature currently offers only 1/3/7-day presets; arbitrary durations are out-of-scope.  
- DeletionQueue growth requires periodic cleanup of completed entries to avoid unbounded tables (future task).

### Future Enhancements (Out of Scope)
- Add quiet hours and per-channel overrides to `/settings`.  
- Allow per-notification overrides (e.g., delete after watching).  
- Surface admin telemetry (dashboard) summarizing deletions per chat.
