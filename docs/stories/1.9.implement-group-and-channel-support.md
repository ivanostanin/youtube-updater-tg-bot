# Story 1.9: Implement Group and Channel Support

## Status

Approved

---

## Story

**As a** Telegram group administrator,  
**I want** to configure YouTube subscriptions for my group,  
**so that** all members receive notifications automatically.

---

## Acceptance Criteria

1. **AC1:** Detect chat type (private, group, supergroup, channel) in all handlers
2. **AC2:** Add admin verification for group/channel commands (check user permissions via Telegram API)
3. **AC3:** Refactor database schema to support multiple chat types:
   - Create new `Chat` model: `id`, `chat_id`, `chat_type`, `title`, `created_at`
   - Update `Subscription` model: Change `user_id` → `chat_id` (foreign key to `chats.id`)
   - Migrate existing user subscriptions to new schema (users become chats with `type='private'`)
4. **AC4:** Implement `/subscribe` command working in groups/channels (admin-only)
5. **AC5:** Implement `/list` showing group/channel subscriptions (admin-only)
6. **AC6:** Implement `/unsubscribe` for groups/channels (admin-only)
7. **AC7:** Send notifications to group/channel chat when new videos are uploaded
8. **AC8:** Add group-specific message formatting (discussion prompt for groups)
9. **AC9:** Update all existing handlers to work with both private chats and groups
10. **AC10:** Create Alembic migration for database schema changes with upgrade/downgrade paths
11. **AC11:** Write migration guide documentation in CLAUDE.md for existing users (if any)
12. **AC12:** Add comprehensive tests (unit tests for admin checks, integration tests for group flows)

## Dev Notes

### Previous Story Insights
- Story 1.3 established stable pytest fixtures and coverage for handlers and repositories, enabling rapid regression detection when we refactor for chat contexts.  
- Story 1.4 (in-progress) will add CI enforcement, so schema and handler changes must maintain green pipelines to unblock deployments.  
- No prior stories have modified subscription schema; replication risk is isolated to this story.

### Architectural Drivers for Multi-Chat Support
- Phase 2 prioritizes group/channel multi-context subscriptions to unlock network effects.  
  *[Source: architecture/2-enhancement-scope-and-integration-strategy.md#212-phase-2-user-experience-enhancements]*
- Service layer introduction (ACL, PreferenceManager) keeps handlers lean and testable.  
  *[Source: architecture/2-enhancement-scope-and-integration-strategy.md#221-code-integration-strategy]*
- Database integration strategy mandates additive migrations with Alembic to avoid downtime.  
  *[Source: architecture/2-enhancement-scope-and-integration-strategy.md#222-database-integration]*

### Data Model & Migration Guidance
- New `Chat` entity stores Telegram chat metadata with unique `chat_id` per context.  
  *[Source: architecture/4-data-models-and-schema-changes.md#411-chat]*
- Subscription model gains optional `chat_id` FK ensuring backward compatibility while enabling group ownership.  
  *[Source: architecture/4-data-models-and-schema-changes.md#421-subscription-phase-1-migration]*
- Migration strategy emphasizes nullable fields, additive indexes, and downgrade paths for rollback.  
  *[Source: architecture/4-data-models-and-schema-changes.md#431-database-changes-required]*

### Component & Service Interactions
- ACLService enforces admin-only workflows and integrates with ChatRepository to register new chats on-demand.  
  *[Source: architecture/5-component-architecture.md#511-aclservice]*
- PreferenceManager and DeletionScheduler rely on chat IDs for scoped settings and auto-deletion timers.  
  *[Source: architecture/5-component-architecture.md#513-preferencemanager; architecture/5-component-architecture.md#512-deletionscheduler]*
- HistoryService and other Phase 2 components depend on accurate chat association for pagination and exports.  
  *[Source: architecture/5-component-architecture.md#514-historyservice]*

### API & Handler Considerations
- Command handlers must maintain backward compatibility while extending to group contexts with admin validation.  
  *[Source: architecture/6-api-design-and-integration.md#61-api-integration-strategy]*
- New command behaviors (`/settings`, `/history`) expect shared service abstractions that also consume chat-aware data.  
  *[Source: architecture/6-api-design-and-integration.md#62-new-bot-commands]*
- Repository/service interfaces follow async patterns to avoid blocking event loop during Telegram API calls.  
  *[Source: architecture/6-api-design-and-integration.md#61-api-integration-strategy]*

### Source Tree Alignment
- New `Chat` model lives in `src/database/models.py`, with migrations under `src/database/migrations/versions/`.  
  *[Source: architecture/8-source-tree.md#82-new-file-organization]*
- Service implementations (`acl.py`, formatters) belong in `src/services/` as defined for Phase 2.  
  *[Source: architecture/8-source-tree.md#82-new-file-organization]*
- Tests mirror structure: `tests/unit/services/test_acl_service.py`, `tests/integration/test_group_flow.py`.  
  *[Source: architecture/8-source-tree.md#82-new-file-organization]*

### Testing Strategy
- Unit coverage targets 80%+ for new service layer components including ACLService and chat repositories.  
  *[Source: architecture/11-testing-strategy.md#1121-unit-tests-for-new-components]*
- Integration tests must simulate end-to-end group flows and verify backward compatibility with private chats.  
  *[Source: architecture/11-testing-strategy.md#1122-integration-tests]*
- Regression suite continues running with SQLite in-memory DB and mocked Telegram API responses.  
  *[Source: architecture/11-testing-strategy.md#111-integration-with-existing-tests]*

### Security & Compliance Considerations
- Admin verification is a critical security requirement to prevent unauthorized group configuration.  
  *[Source: architecture/12-security-integration.md#122-enhancement-security-requirements]*
- Security tests must cover ACL bypass attempts and rate limiting for group commands.  
  *[Source: architecture/12-security-integration.md#123-security-testing]*
- Secrets remain managed via environment settings; migration scripts must avoid logging sensitive data.  
  *[Source: architecture/12-security-integration.md#121-existing-security-measures]*

### Integration Verification Requirements
- **IV1:** Existing personal subscriptions migrate successfully to new schema (validated via Alembic migration tests).  
- **IV2:** Private chat subscription flow remains functional (`/subscribe`, `/list`, `/unsubscribe`).  
- **IV3:** Group admin verification allows authorized commands and rejects non-admins with informative message.  
- **IV4:** Group notifications deliver with discussion prompts and respect preference hooks.  
- **IV5:** Webhook processing continues to route updates correctly after schema change.  
- **IV6:** Full pytest suite passes (unit + integration) with new schema using CI pipeline.

### Risk Mitigation
- Feature flags or configuration toggles may disable group flows temporarily if migration issues surface.  
- Provide rollback plan via Alembic downgrade, plus database backups prior to deployment.  
- Run migration dry-run against staging backup before production rollout.

### Known Limitations
- Telegram API rate limits may slow admin verification for large groups; consider caching results.  
- Existing analytics may not differentiate between user vs. chat subscriptions until updated.  
- Notification formatting for channels lacking discussion groups may need iterative improvements.

### Future Enhancements (Out of Scope)
- Introduce role-based access (co-admins vs. owners) for granular permissions.  
- Add preference-managed message templates per chat.  
- Expand `/history` command to support group-level exports with filters.
