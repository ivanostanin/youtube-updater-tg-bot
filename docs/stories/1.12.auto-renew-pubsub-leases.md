# Story 1.12: Auto-Renew PubSub Hub Leases

## Status

Ready for Review

---

## Story

**As a** reliability engineer responsible for keeping real-time channel notifications alive,  
**I want** the bot to capture `hub.lease_seconds` metadata and renew PubSub subscriptions before they expire,  
**so that** channels never silently stop delivering updates while at least one bot subscription remains active.

---

## Acceptance Criteria

1. **AC1 (Webhook lease metadata capture):** `src/webhooks/handlers.py` must parse `hub.mode`, `hub.topic`, `hub.lease_seconds`, and `hub.challenge` on every verification request. When `hub.mode=subscribe`, derive the channel_id from `hub.topic`, persist the received lease duration, computed `lease_expires_at` (request timestamp + lease_seconds), last verification timestamp, and the callback URL that responded. Missing `hub.lease_seconds` values default to 86 400 seconds with a WARN log so leases are still tracked. When `hub.mode=unsubscribe`, the lease metadata for that channel is cleared without affecting unrelated channels. Responses must still echo `hub.challenge` to satisfy PubSubHubbub.
2. **AC2 (Schema & repository support):** Add Alembic migration(s) that introduce lease-tracking columns on `youtube_channels` (e.g., `webhook_callback_url`, `webhook_lease_seconds`, `webhook_lease_expires_at`, `webhook_last_verified_at`). Update SQLAlchemy models plus `ChannelRepository` / `SubscriptionRepository` helpers to read and write the new fields, and backfill existing rows by copying the most recent non-null `Subscription.webhook_url` (falling back to `settings.webhook_callback_url`). Migrations must be idempotent across SQLite and PostgreSQL.
3. **AC3 (Automatic lease refresh service):** Implement a `WebhookLeaseRefresher` (or extend `WebhookSubscriptionSynchronizer`) that runs on a configurable interval (default hourly) via the Telegram application `job_queue` or background task. The job queries channels whose `webhook_lease_expires_at` is missing or within the configurable `LEASE_RENEWAL_THRESHOLD` window (default 6 hours), confirms that at least one active subscriber exists, and calls `PubSubManager.subscribe_to_channel` to renew the hub lease. Successful renewals persist the new lease metadata and log structured context (`channel_id`, seconds granted, next expiry); failures raise ERROR logs and schedule retries without crashing the bot.
4. **AC4 (Inactive subscription guardrails):** The refresher must skip channels when all related bot subscriptions are inactive or `notification_enabled=False`. When the last active subscription is removed, the system clears any stored lease metadata and, if we previously subscribed, issues a best-effort `hub.mode=unsubscribe` call so the hub stops sending traffic. This ensures the “auto-renew” path never resurrects intentionally disabled subscriptions.
5. **AC5 (Observability, configuration, and tests):** Add new settings (e.g., `PUBSUB_LEASE_RENEWAL_INTERVAL`, `PUBSUB_LEASE_RENEWAL_THRESHOLD`) with sane defaults and documentation in `.env.example`, README, and CLAUDE.md. Extend the pytest suite with unit tests covering: (a) webhook handler persisting lease data, (b) repository query that selects renew-ready channels, and (c) refresher job behavior for renew/skip paths. Include structured DEBUG/INFO logs that match the logging blueprint from Story 1.11 and add metrics counters or gauges where appropriate.

## Dev Notes

### Current PubSub Handling Baseline

- `src/webhooks/handlers.py:14-75` currently echoes `hub.challenge` and immediately returns, so it never inspects `hub.topic` or `hub.lease_seconds`. The new logic must remain non-blocking (no DB writes after `Response(challenge)`) by persisting metadata before replying.  
- `src/webhooks/pubsub.py` already centralizes subscribe/unsubscribe calls; re-use it for renewals so HTTP headers, timeouts, and local-short-circuit logic stay consistent.  
- `src/webhooks/synchronizer.py` refreshes subscriptions only when webhook URLs change. Extending it or adding a dedicated refresher should not regress that behavior; keep the “legacy vs. current callback” checks intact.

### Data Model & Repository Impact

- `src/database/models.py` defines `YouTubeChannel` and `Subscription`. Neither has lease columns today, so the migration must extend `YouTubeChannel` (channel-level lease state) while leaving individual subscription records focused on chat ownership.  
- `src/database/repository.py` already has helpers such as `get_channel_subscribers`. Add composable queries that filter by `Subscription.is_active` and `notification_enabled`, and surface a lightweight DTO (channel_id, webhook_url, lease_expires_at) for the refresher job.  
- Remember that migrations must support SQLite (dev) and PostgreSQL (future Story 1.10). Use SQLAlchemy types that work in both engines and add `server_default=None` to keep alembic autogeneration predictable.

### Runtime & Scheduling Considerations

- `YouTubeUpdaterBot.initialize()` (src/bot/bot.py:17-86) already kicks off `WebhookSubscriptionSynchronizer.run()` during startup and registers a heartbeat job via `job_queue`. Hook the lease refresher into that same queue so it benefits from the Telegram Application lifecycle (automatic cancellation on shutdown).  
- New configuration knobs should live in `src/utils/config.py`, using `pydantic` validation to ensure intervals are positive integers. Mirror them in `.env.example` and document expected units (seconds or minutes).  
- When the last subscription disappears (e.g., `/unsubscribe` flow in `src/bot/handlers.py`), ensure lease metadata and active leases are cleaned up, otherwise the refresher will keep renewing ghost subscriptions.

### Testing & Tooling References

- Follow the async pytest guidance in `docs/architecture/11-testing-strategy.md` and re-use fixtures from `tests/conftest.py` for database sessions and mocked PubSub clients.  
- Existing suites (`tests/unit/test_pubsub.py`, `tests/unit/test_webhook_synchronizer.py`) show how PubSub HTTP calls are mocked; align the new refresher tests with those patterns and add Allure feature/story tags per Story 1.3 conventions.

### Risks & Edge Cases

- PubSub sometimes omits `hub.lease_seconds`; defaulting to 86 400 seconds (24h) prevents the state machine from stalling but should emit a warning so operators can investigate.  
- Avoid thundering-herd renewals by batching/spacing API calls (e.g., reusing the same `httpx.AsyncClient` and awaiting between calls).  
- Ensure time math uses UTC-aware `datetime` objects; mixing naive timestamps breaks comparisons when the refresher job runs in containers with different TZ settings.  
- When a hub renewal fails repeatedly, surface metrics/logs so operators can act before subscriptions lapse.

### Integration Verification Requirements

- **IV1:** Simulate a `hub.mode=subscribe` GET request (via pytest or a manual curl) and confirm the channel row records lease_seconds, expires_at, last_verified_at, and the callback URL that responded.  
- **IV2:** With at least one active subscription present, advance the clock so a lease is within the renewal threshold and verify the refresher job issues `hub.mode=subscribe`, updates the lease metadata, and logs the renewal.  
- **IV3:** Remove the final active subscription for a channel and confirm the system clears lease metadata, skips renewal attempts, and performs a best-effort `hub.mode=unsubscribe`.

### Definition of Done

- All acceptance criteria met with supporting automated tests and documentation.  
- Alembic migrations applied locally (SQLite) and validated via `uv run alembic upgrade head`.  
- New worker runs automatically in dev/staging with observable logs/metrics.  
- Story marked “Ready for Dev” only after reviewers confirm guardrails prevent renewing inactive subscriptions.
