# Story 1.8: Implement Update History with Filtering (Phase 2 Feature)

## Status

Draft
---

## Story

**As a** Telegram user,  
**I want** to view my notification history with filtering options,  
**so that** I can find past videos I missed or want to watch later.

---

## Acceptance Criteria

1. **AC1:** Implement `/history` command showing last 10 notifications with video title, channel, date, link  
2. **AC2:** Add pagination using inline keyboard (Next/Previous buttons with page tracking)  
3. **AC3:** Implement `/history <channel_name>` to filter by specific channel (fuzzy match on name)  
4. **AC4:** Add date range filtering: `/history 7d` (last 7 days), `/history 30d`, `/history 90d`  
5. **AC5:** Display format: "📺 [Channel] - [Video Title]\n⏰ [Date]\n🔗 [Link]"  
6. **AC6:** Limit history to last 90 days (performance optimization, configurable)  
7. **AC7:** Update help text with new command documentation  
8. **AC8:** Add unit tests for filtering logic, integration test for command flow  

*(Source: docs/prd/4-epic-story-structure.md#story-18-implement-update-history-with-filtering; docs/prd/2-requirements.md#fr9-the-system-shall-maintain-a-searchable-history-of-sent-notifications-with-filtering-by-channel-date-range-and-keyword)*

- [ ] **Task 1: Implement HistoryService data access and filtering (AC: 1, 3, 4, 6)**  
  - [ ] Create `HistoryService` in `src/services/history.py` (or extend if scaffolded) that queries `NotificationRepository` with joins to channel metadata so each row includes title, channel, timestamp, and video URL.  
  - [ ] Add `HistoryFilters` dataclass (channel term, date range, chat/user context) plus helper to cap queries to configurable retention (default 90 days, override via env var/Settings).  
  - [ ] Support fuzzy channel matching (e.g., `ILIKE '%term%'`) while ensuring indexes on `channel_id`/`sent_at` are used; fall back to channel slug/id detection when the user passes a URL or handle.  
  - [ ] Return a `HistoryPage` structure containing results, total count, current page, total pages, and callback tokens for pagination.

## Dev Notes

### HistoryService Responsibilities
- Encapsulate all history queries inside `src/services/history.py` so bot handlers remain thin; leverage repository pattern for composable filters.  
  *[Source: docs/architecture/5-component-architecture.md#514-historyservice; docs/architecture/2-enhancement-scope-and-integration-strategy.md#221-code-integration-strategy]*
- Prefer returning DTOs with preformatted strings to minimize formatting duplication in handlers; keep pagination metadata alongside results.  
  *[Source: docs/architecture/5-component-architecture.md#514-historyservice]*

### Filtering & Performance
- Use indexed columns (`chat_id_sent_to`, `sent_at`, `channel_id`) and add partial indexes if necessary to keep `/history` under the 500 ms p95 performance budget.  
  *[Source: docs/prd/4-epic-story-structure.md#story-18-implement-update-history-with-filtering; docs/prd/2-requirements.md#fr9-the-system-shall-maintain-a-searchable-history-of-sent-notifications-with-filtering-by-channel-date-range-and-keyword; docs/prd/2-requirements.md#nfr5-database-queries-shall-use-appropriate-indexes-on-telegram_id-channel_id-video_id-and-chat_id-fields]*
- Fuzzy matching should fall back to deterministic identifiers to avoid table scans; cache canonical channel IDs per user/chat when possible.  
  *[Source: docs/prd/4-epic-story-structure.md#story-18-implement-update-history-with-filtering; docs/architecture/6-api-design-and-integration.md#622-history]*
- Enforce retention cap before query execution to limit dataset size, but allow administrators to increase the limit through configuration with warnings in docs.  
  *[Source: docs/prd/4-epic-story-structure.md#story-18-implement-update-history-with-filtering]*

### Telegram UX & Pagination
- Inline keyboards should mirror existing emoji-first style; callback payloads must include filters/page info so pagination works even if the user taps buttons minutes later.  
  *[Source: docs/architecture/6-api-design-and-integration.md#622-history; docs/architecture/2-enhancement-scope-and-integration-strategy.md#233-uiux-consistency]*
- Guard against Telegram 409/too-old-callback errors by validating callback age and re-sending a fresh history list when needed.  
  *[Source: docs/architecture/6-api-design-and-integration.md#622-history; docs/architecture/12-security-integration.md#telegram-bot-hardening]*

### Testing Strategy
- Unit tests go under `tests/unit/services/test_history_service.py`; integration tests can reuse bot fixtures to simulate command/callback flows and verify formatting plus pagination.  
  *[Source: docs/architecture/11-testing-strategy.md#1121-unit-tests-for-new-components; docs/architecture/11-testing-strategy.md#1122-integration-tests; docs/architecture/8-source-tree.md#82-new-file-organization]*
- Include regression assertions to confirm notification delivery and unsubscribe flows still pass after history queries (no locking or slowdowns).  
  *[Source: docs/architecture/11-testing-strategy.md#113-regression-testing]*

### Integration Verification Requirements
- **IV1:** History command doesn't interfere with notification delivery.  
- **IV2:** Pagination works correctly with >10 results (test with user having 50+ notifications).  
- **IV3:** Filtering returns accurate results (test with known data).  
- **IV4:** Command responds within 500 ms for typical queries (indexed lookups).  
- **IV5:** Works in both private chats and groups (group history = shared history for that chat).  
  *[Source: docs/prd/4-epic-story-structure.md#story-18-implement-update-history-with-filtering]*
