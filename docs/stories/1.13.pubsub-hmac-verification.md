# Story 1.13: Enforce PubSub HMAC Signatures

## Status

Draft

---

## Story

**As a** security engineer responsible for the bot’s webhook perimeter,  
**I want** every PubSub notification to be authenticated with HMAC signatures end-to-end,  
**so that** spoofed YouTube events can’t trigger false notifications or exhaust bot resources.

---

## Acceptance Criteria

1. **AC1 (Hub secret configuration & handshake):** Introduce a `PUBSUB_HMAC_SECRET` (32+ random bytes, base64-safe) setting in `src/utils/config.py`/`.env.example`. `PubSubManager.subscribe_to_channel()` and `unsubscribe_from_channel()` must include `hub.secret` for all non-local callbacks, reuse it when refreshing subscriptions, and refuse to start (ERROR + exit) if the secret is missing in production. Local callbacks (`localhost`/loopback) may omit the secret but must log a WARN explaining signatures are bypassed. *(Sources: docs/prd/3-technical-constraints-integration.md §PubSubHubbub Integration; src/webhooks/pubsub.py)*
2. **AC2 (Webhook signature verification):** `WebhookHandlers.youtube_webhook` validates `X-Hub-Signature` and `X-Hub-Signature-256` headers on every POST notification and verification ping. The handler computes HMAC-SHA1/SHA256 over the raw request body using the configured secret, compares against the header, and returns `403` with structured logging + metric increment when signatures are missing or invalid. Successful checks emit DEBUG logs with `channel_id`, `signature_algo`, and byte length; failures must never leak the secret. *(Sources: docs/prd/3-technical-constraints-integration.md; docs/prd/5-appendix.md link to PubSubHubbub spec; src/webhooks/handlers.py)*
3. **AC3 (Secret lifecycle & synchronization):** Persist a per-callback secret fingerprint (e.g., SHA-256 digest) on the channel record so `WebhookSubscriptionSynchronizer` can detect drift between the stored secret and the current `settings.pubsub_hmac_secret`. When drift is found, the synchronizer must reissue subscribe requests with the new `hub.secret`, update the fingerprint, and log rotation progress. Schema updates (Alembic + SQLAlchemy models + repositories) must remain backward-compatible across SQLite/PostgreSQL, defaulting existing rows to “no fingerprint.” *(Sources: docs/architecture/5-component-architecture.md §WebhookSubscriptionSynchronizer; src/webhooks/synchronizer.py; src/database/models.py)*
4. **AC4 (Tests & observability):** Extend `tests/unit/test_pubsub.py` (and/or new tests) to cover handshake payload generation with secrets, and add webhook handler tests (unit or Starlette integration) that assert valid signatures return `200` while tampered bodies yield `403`. Add metrics/logging assertions (e.g., via `caplog`) and Allure tags referencing this story. Expose counters/gauges for signature failures (`pubsub_signature_failures_total`) and include them in the monitoring strategy (`CLAUDE.md`). *(Sources: docs/architecture/11-testing-strategy.md; docs/stories/1.3.setup-comprehensive-test-suite.md §Testing Targets)*
5. **AC5 (Documentation & ops guardrails):** Update `.env.example`, `README.md`, and `CLAUDE.md` with guidance on generating/rotating the HMAC secret, limitations for local development, and the required redeploy steps (rotate secret → run synchronizer → verify metrics). Document the rollback path (clear fingerprint, revert secret, rerun synchronizer) and highlight that secrets must never be committed to git. *(Sources: docs/prd/3-technical-constraints-integration.md; docs/architecture/12-security-integration.md §Enhancement Security Requirements)*

## Dev Notes

### PubSub/Webhook Baseline

- `PubSubManager` currently handles subscribe/unsubscribe/verify flows but never sends `hub.secret`, meaning the hub cannot include `X-Hub-Signature` headers for authenticity (`docs/prd/3-technical-constraints-integration.md`, `src/webhooks/pubsub.py`).  
- `WebhookHandlers.youtube_webhook` simply echoes verification challenges and trusts every POST body parsed via `feedparser`, leaving the bot open to spoofed feeds (`src/webhooks/handlers.py`).  
- The synchronizer in `src/webhooks/synchronizer.py` refreshes callbacks when the URL changes, which is the right place to piggyback secret rotations (`docs/architecture/5-component-architecture.md#webhooksubscriptionsynchronizer`).

### Configuration & Secrets

- Runtime settings live in `src/utils/config.py`, loaded via `.env`; no PubSub-specific secret exists today. Adding `PUBSUB_HMAC_SECRET` keeps consistency with other sensitive settings (telegram token, API key).  
- `.env.example`, `README.md`, and `CLAUDE.md` document required env vars and operational playbooks (`docs/architecture/12-security-integration.md`). Make sure new guidance covers secret length, storage in secrets manager, and rotation cadence.  
- Local development frequently uses `http://localhost:8000/webhook/youtube`; mimic `_short_circuit()` so local runs can skip secret enforcement with clear WARN logs.

### Data & Repository Touchpoints

- Channel discovery + subscriber checks already happen via `ChannelRepository`/`SubscriptionRepository` (`src/database/repository.py`). Persisting a fingerprint alongside the channel allows one-to-many subscriptions to stay in sync without duplicating data.  
- Alembic migrations live under `alembic/versions/`; follow existing patterns for SQLite/PostgreSQL compatibility and include downgrade steps (`docs/architecture/4-data-models-and-schema-changes.md`).  
- Any fingerprint write should happen inside the same transaction that updates subscription webhook URLs so state stays consistent.

### Testing Expectations

- Follow the test pyramid + Allure tagging described in `docs/architecture/11-testing-strategy.md` and `docs/stories/1.3.setup-comprehensive-test-suite.md`.  
- Unit tests belong in `tests/unit/test_pubsub.py`, `tests/unit/test_webhook_handlers.py` (add if missing), and repository tests for fingerprint persistence.  
- Integration tests in `tests/integration/test_webhook_server.py` (or new file) should simulate signed/unsigned POSTs using Starlette’s test client to validate end-to-end rejection of tampered payloads.

### Observability & Metrics

- Story 1.11 established structured logging expectations; reuse the same context keys when logging signature verification attempts (`docs/stories/1.11.debug-logging-instrumentation.md`).  
- Emit counters/gauges compatible with the monitoring plan from `docs/architecture/9-infrastructure-and-deployment.md#logging-and-monitoring`, e.g., `pubsub_signature_failures_total` and `pubsub_signed_notifications_total`.

### Risks & Constraints

- **Secrets in logs:** Never log the raw secret; only log truncated fingerprints or hash prefixes.  
- **Hub mismatch:** YouTube’s hub may delay delivering notifications until subscriptions are renewed with the new secret; ensure synchronizer retries and does not drop subscribers mid-rotation.  
- **Backward compatibility:** Existing channels without fingerprints must continue receiving notifications until the synchronizer updates them.

### Definition of Done

- All acceptance criteria satisfied with passing unit/integration tests and updated documentation.  
- Signature metrics/logs verified manually (e.g., `pytest -k signature` + local webhook curl).  
- Secret rotation runbook validated in staging or via automated test to ensure synchronizer resubscribes channels.  
- Story status moved to “Ready for Dev” once scope, tasks, and notes are complete.
