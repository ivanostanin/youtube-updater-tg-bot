## Story

**As a** developer,  
**I want** automated testing and Allure reports on every commit,  
**so that** I can catch regressions early and track test results over time.

1. **AC1:** Create `.github/workflows/test.yml` workflow file
2. **AC2:** Workflow runs on push to main and all pull requests
3. **AC3:** Workflow installs dependencies and runs pytest with Allure

5. **AC5:** Workflow uploads Allure report as GitHub Actions artifact (30-day retention)
6. **AC6:** Configure GitHub Pages deployment for Allure reports at `https://ivanostanin.github.io/youtube-updater-tg-bot/allure-latest/`
7. **AC7:** Add status badge to README.md showing test pass/fail status
8. **AC8:** Workflow fails PR if tests fail (blocks merge)

## Dev Notes

### Previous Story Insights
- Story 1.3 delivered a comprehensive pytest suite with Allure decorators and 98 tests, confirming CI can rely on `pytest --alluredir=allure-results` for coverage.  
- Test suite execution completes well under 5 minutes, aligning with CI duration targets.  
- QA emphasized maintaining Allure metadata coverage (90.8%), so CI must preserve Allure output integrity.

### CI/CD Pipeline Expectations
- GitHub Actions is the standardized pipeline orchestrator, with staged jobs for lint, test, build, and deploy.  
  *[Source: architecture/9-infrastructure-and-deployment.md#92-enhancement-deployment-strategy]*
- Workflows should support blue-green style promotions and provide artifact retention for audits.  
  *[Source: architecture/9-infrastructure-and-deployment.md#92-enhancement-deployment-strategy]*
- Manual approval gates exist for production deployments; CI must expose clear status checks for gating.  
  *[Source: architecture/9-infrastructure-and-deployment.md#92-enhancement-deployment-strategy]*

### Tech Stack & Tooling Alignment
- Python 3.13 is the mandated runtime; selecting other versions in CI may introduce incompatibilities.  
  *[Source: architecture/3-tech-stack.md#31-existing-technology-stack]*
- Ruff, mypy, pytest, and allure-pytest are core dev dependencies expected in the workflow.  
  *[Source: architecture/3-tech-stack.md#31-existing-technology-stack]*
- Alembic and other optional extras should not be installed unless required by the job to keep runtimes fast.  
  *[Source: architecture/3-tech-stack.md#32-new-technology-additions]*

### Source Tree Alignment
- Repository already reserves `.github/workflows/` for CI pipeline definitions; new workflow should reside there.  
  *[Source: architecture/8-source-tree.md#81-existing-project-structure]*
- Test suite lives under `tests/` mirroring `src/`, ensuring `pytest` discovery paths remain default-friendly.  
  *[Source: architecture/8-source-tree.md#82-new-file-organization]*
- Documentation updates for CI belong in `CLAUDE.md` under operator guidance sections.  
  *[Source: architecture/8-source-tree.md#82-new-file-organization]*

### Testing Strategy
- CI must execute both unit and integration tests, honoring pytest markers and async fixtures.  
  *[Source: architecture/11-testing-strategy.md#111-integration-with-existing-tests]*
- Regression suite should remain stable (<5 minute runtime) with reliable fixtures and no flaky tests.  
  *[Source: architecture/11-testing-strategy.md#113-regression-testing]*
- Allure report generation enables traceability for Given-When-Then scenarios tied to acceptance criteria.  
  *[Source: architecture/11-testing-strategy.md#1122-integration-tests]*

### Security & Compliance Considerations
- Workflow secrets (bot token, API keys) must be referenced via GitHub Actions secrets; never echo to logs.  
  *[Source: architecture/12-security-integration.md#122-enhancement-security-requirements]*
- Admin ACL and rate limiting enforcement rely on consistent CI coverage to prevent regressions.  
  *[Source: architecture/12-security-integration.md#123-security-testing]*
- Dependabot and pre-commit hooks complement CI; ensure pipeline surfaces issues swiftly.  
  *[Source: architecture/12-security-integration.md#121-existing-security-measures]*

### Integration Verification Requirements
- **IV1:** Trigger workflow on feature branch and main to confirm automation runs.  
- **IV2:** Validate pytest succeeds in GitHub-hosted Ubuntu environment.  
- **IV3:** Confirm Allure artifact appears in Actions run artifacts tab.  
- **IV4:** Ensure workflow status gate blocks merges when tests fail.

### Risk Mitigation
- Cache dependencies to minimize runtime variability and reduce flake potential.  
- Add retry logic or install mirrors for Allure CLI download to avoid transient network failures.  
- Document fallback for Pages publishing (manual artifact download) if GitHub Pages unavailable.

### Known Limitations
- Workflow depends on GitHub-hosted runners with internet access; self-hosted runners need extra setup for Allure CLI.  
- Allure CLI download source may change; pin specific release URL to reduce breakage.  
- GitHub Pages deployment may take several minutes; report availability is not instantaneous.

### Future Enhancements (Out of Scope)
- Add matrix runs for multiple Python versions and OS targets.  
- Integrate coverage reporting with Codecov or GitHub Code Coverage API.  
- Automate Slack/Telegram notifications for workflow failures.

## QA Results

### Review Date: 2025-11-09

### Reviewed By: Quinn (Test Architect)

### Executive Summary

**Gate Status: ❌ FAIL** — Workflow implementation is close, but two blocking issues prevent acceptance: (1) the workflow token permissions disable all artifact uploads, so the run cannot finish successfully, and (2) no Allure HTML artifact is retained for 30 days as required by AC5.

### Detailed Findings

1. **Blocking – Artifact uploads denied (AC5, AC6 evidence chain)**  
   `.github/workflows/test.yml:12-14,57-86` limits the workflow token to `contents: read`, implicitly revoking `actions: write`. As a result, `actions/upload-artifact@v4` and `actions/upload-pages-artifact@v3` will fail with `Resource not accessible by integration`, so the run cannot retain Allure evidence nor hand off the Pages bundle for deployment.
2. **Blocking – Allure HTML report not stored as a 30-day artifact (AC5)**  
   The pipeline only uploads the raw `allure-results` directory. AC5 explicitly requires the generated HTML report to be available as a GitHub Actions artifact with 30-day retention. Without an `actions/upload-artifact` step targeting `allure-report`, consumers cannot download the rendered report for audit/review.
