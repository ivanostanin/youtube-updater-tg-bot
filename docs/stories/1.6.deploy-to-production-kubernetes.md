# Story 1.6: Deploy to Production Kubernetes

## Status

Draft
---

## Story

**As a** DevOps engineer,  
**I want** the bot deployed to the production Kubernetes cluster with versioned CI/CD releases, secrets, and persistence,  
**so that** end users experience a reliable, traceable service backed by modular deployment workflows.

---

## Acceptance Criteria

1. **AC1:** Modular GitHub Actions pipeline treats `push` events on annotated tags matching `v*` as release runs, reusing the existing test/build jobs and adding a release stage that builds `deployment/docker/Dockerfile`, signs the artifact, and publishes Docker images tagged with the semver (`vX.Y.Z`), commit SHA, and (when on the default branch) `latest`.  
2. **AC2:** Production Helm values (e.g., `deployment/helm/youtube-updater-tg-bot/values-prod.yaml`) pin the released image tag (initial target `v0.2.0`), document the corresponding chart version, and are referenced in release notes so operators can run `helm upgrade ... -f values-prod.yaml`.  
3. **AC3:** Kubernetes secrets exist for `TELEGRAM_BOT_TOKEN`, `YOUTUBE_API_KEY`, `WEBHOOK_CALLBACK_URL`, and backup credentials either via native Secret manifests or External Secrets Operator, and the Helm chart references them without inlining sensitive values.  
4. **AC4:** Helm chart deploys with production-ready settings (PVC sized ≥10 Gi, init container running migrations/restore, resource requests 500m/512 Mi, readiness & liveness probes hitting `/health`) aligned with the current deployment strategy.  
5. **AC5:** Ingress exposes `https://youtube-bot.nmro.cc` with TLS (Let's Encrypt or managed cert), maps the webhook path, and validates certificate status via `kubectl describe certificate` or equivalent controller logs.  
6. **AC6:** End-to-end smoke tests in production verify private chat subscription flows, group admin subscription approvals, and rejection paths for non-admins, recording evidence (logs or screen captures).  
7. **AC7:** Alerting exists for pod restarts and critical errors by wiring Prometheus metrics / Kubernetes events into the existing monitoring stack (e.g., Grafana Alerting or PagerDuty) with documented thresholds.  
8. **AC8:** Database persistence is verified by forcing a pod restart, confirming the PVC keeps `bot.db`, and demonstrating subscriptions remain intact afterward.

## Integration Verification Requirements

- **IV1:** Bot responds to `/start` and `/status` in production after deployment.  
- **IV2:** Existing subscriptions continue receiving notifications post-upgrade (no data loss).  
- **IV3:** Webhook callbacks from YouTube reach `https://youtube-bot.nmro.cc/webhook/...` and appear in logs.  
- **IV4:** Database persists across pod restarts (PVC mounted at `/data`).  
- **IV5:** Metrics endpoint (`/metrics`) and health check (`/health`) return 200 after deployment.  
- **IV6:** Alerting fires (or at least test notifications) when pods crash or error rate exceeds the defined threshold.  
- **IV7:** Tagging a release (e.g., `git tag v0.2.0 && git push origin v0.2.0`) triggers the modular CI/CD workflow, publishes the Docker image with semver/SHA/latest tags, and stores release notes referencing the deployed Helm values.

## Dev Notes

### Deployment Baseline Alignment
- Current infrastructure already uses Docker + Helm on an OCI-managed Kubernetes cluster, so this story focuses on hardening the existing chart rather than inventing a new deployment method.  
  *[Source: docs/architecture/9-infrastructure-and-deployment.md#91-existing-infrastructure; docs/architecture/8-source-tree.md#81-existing-project-structure]*  
- Rolling updates with `maxUnavailable=0`/`maxSurge=1` are mandatory to avoid downtime and align with the production readiness plan.  
  *[Source: docs/prd/3-technical-constraints-integration.md#deployment-strategy]*  

### CI/CD & Version Tagging Expectations
- The GitHub Actions workflow already runs tests/builds; this story extends it with a tag-driven release stage so operators can trust the provenance of published Docker images.  
  *[Source: .github/workflows/main.yml; docs/prd/3-technical-constraints-integration.md#deployment-strategy]*  
- Docker Hub must contain semver-tagged images for traceability, while `latest` continues to track the default branch; provenance attestations maintain supply-chain integrity.  
  *[Source: docs/architecture/9-infrastructure-and-deployment.md#deployment-approach; user request 2025-02-??]*  

### Secrets, Persistence, and Backups
- Secrets for Telegram, YouTube, and OCI access remain in Kubernetes Secrets or External Secrets Operator manifests; no secret data belongs in Git.  
  *[Source: docs/prd/2-requirements.md#non-functional-requirements; docs/prd/3-technical-constraints-integration.md#kubernetes-deployment]*  
- SQLite persistence relies on PVC + backup CronJob delivered in Story 1.2; ensure their hooks stay active during Helm upgrades.  
  *[Source: docs/stories/1.2.database-backup-to-s3.md#dev-notes]*  

### Testing Strategy for Deployments
- Smoke tests should reuse Story 1.3’s suite and Story 1.4’s CI logs where possible to avoid duplicating coverage.  
  *[Source: docs/prd/4-epic-story-structure.md#story-13-setup-comprehensive-test-suite; docs/prd/4-epic-story-structure.md#story-14-configure-github-actions-ci-cd-with-allure-reports]*  
- Manual validations (group chat permission checks, webhook callbacks) must be documented with timestamps and Telegram chat IDs for auditability.  

### Risk Mitigation
- **Secrets exposure:** Validate manifests via policy-as-code (e.g., `kubectl diff`) before applying; rely on External Secrets Operator where possible.  
- **Ingress/TLS drift:** Automate certificate renewals and monitor via controller metrics to avoid outages.  
- **Tagging mistakes:** Protect the `v*` namespace (require signed tags or approvals) to keep releases trustworthy.  

### Known Limitations
- SQLite persistence satisfies current scale but may require PostgreSQL (Story 1.10+) for multi-region deployments.  
- Alerting hooks depend on the monitoring stack delivered in Story 1.5; if Grafana/Prometheus isn’t fully wired, temporary alertmanager webhooks may be needed.  

### Future Enhancements (Out of Scope)
- Blue/green or canary rollouts controlled via feature flags.  
- Automated Helm releases via GitOps (Argo CD/Flux).  
- Full SBOM publishing to attest image dependencies.
